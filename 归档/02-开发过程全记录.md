## 0. 项目起点：一张需求单（2026-09-05）

项目所有者是"知道 Git 重要但一直不会用"的开发者：教程是黑窗口+英文报错，改来改去只能把文件夹存成"最终版""最终版2""最终版真的不改了"。2026-09-05 写下需求单（原文）：

> 我知道 git 是开发时经常需要的一个版本控制工具，但是我不会使用。
> 帮我开发一个 win 端的可视化工具，把 git 的各个功能封装为功能按钮，
> 但需要展示出在点击时执行了什么命令，并给出执行过程和结果。
> 保留日志。执行过程最好也加入进度条。可以在界面中使用终端这样的界面展示内容。
> 这个工具中还要附注使用说明，说明各个功能是做什么用的，应该什么时候进行使用。

一个藏着的小心思："我不只是想要按钮，我还想看着命令学"——**按钮是拐杖，命令才是腿**。所以"命令预览 + 终端回显"不是技术选型，是需求本身。开发方式：作者与 AI 结对（作者出需求、当第一个用户、做每一轮取舍；AI 出手速）。当天产出 v1.0 和 v1.1 两个版本。

## 3. v1.1（09-05 当晚）：第一轮折腾——点【提交】总是失败

### 3.1 现象

程序能打开，【查看状态】【暂存全部】正常，一点【提交】就报：

```
失败：退出码 128
Author identity unknown
*** Please tell me who you are.
```

对不会 Git 的人等于死胡同：不知道它在说什么，也不知道该怎么办。

### 3.2 排查过程（三步，逐步排除）

1. `python -m py_compile git_visual_tool.py` —— 语法通过，排除代码写错；
2. 写自动化冒烟测试：临时目录建真实仓库，模拟点击按钮、跑真实 git 命令——核心执行器（后台线程跑 git、输出回传终端）工作正常，排除执行链路；
3. 跑到"提交"一步复现失败，翻日志看到报错原文；再执行 `git config --global user.name`，**输出为空**——这台电脑从未配置过 Git 身份，根因锁定。

### 3.3 根因

Git 规定每次提交必须记录作者（姓名+邮箱）。这个信息**不是装完 Git 就有的**，需要用户配置一次；不配置，所有提交必定失败，而报错是英文，新手无法理解。

### 3.4 修复（五件）

1. **新增【配置身份】按钮**：填一次姓名邮箱，自动连续执行 `git config --global user.name` / `user.email` 两条命令（队列机制），命令、过程、结果照常显示并写日志；全局生效，只需一次；
2. **失败自动诊断**：任何命令失败后分析 stderr，中文提示常见原因（v1.1 覆盖 6 种：未配置身份/不是仓库/合并冲突/推送被拒/登录权限/无可提交内容）；"未配置身份"还直接弹窗问"是否现在配置？"，确认即打开输入窗口；
3. **启动预检**：打开工具就检测身份，没配置提前在终端提醒"首次提交会失败，请先点【配置身份】"，而不是等提交失败才发现；
4. 顺手修状态栏中文乱码（分支名等输出按 utf-8/gbk 降级解码）；
5. 使用说明页同步更新：快速上手第一步改为"配置身份"，FAQ 加对应条目。

### 3.5 验证（端到端，环境隔离）

用 `GIT_CONFIG_GLOBAL` 环境变量把"全局配置"指到临时文件，不污染真实环境，四项场景全过：启动时正确显示"尚未配置身份"警告 ✅ / 未配置时提交失败+中文提示+弹引导窗 ✅ / 配置后两条 config 命令队列连续执行、姓名邮箱写入 ✅ / 再次提交成功 ✅。

### 3.6 沉淀

> **教训：给新手用的工具，不能假设任何前置知识。** 报错必须翻译成人话，缺什么就引导补什么。

这句话后来成为项目第一原则，也写进了博客。

## 4. v1.2（09-05~06）：第二轮折腾——双击运行闪退

### 4.1 现象

双击 `启动Git工具.bat`，黑窗口一闪而过，界面根本没出来。没有报错、没有弹窗，像什么都没发生过——这种 bug 最抓狂的地方是"你连它死前说什么都不知道"。

### 4.2 排查过程

1. cmd 手动 `where python`、`python --version` —— Python 3.13.9 正常，排除"没装 Python"；
2. **把 bat 的输出重定向到文件再跑**，抓到关键报错：`命令语法不正确。`，且 8 秒后没有任何 python 进程存活——程序压根没被启动；
3. `od -c` 查看文件头字节：每行结尾是 `\n`（LF，Unix 换行）而非 `\r\n`（CRLF，Windows 换行）——真相锁定。

### 4.3 根因（三层问题叠在一起）

1. **致命伤：换行符不对。** cmd.exe 解析批处理要求 CRLF。这个 bat 是类 Unix 工具写的，保存成 LF，导致 `if (...)` 括号块解析错乱，直接报"命令语法不正确"退出——这就是闪退；
2. **隐藏 bug：`%errorlevel%` 在括号块里不生效。** 原 bat 写的是 `if (...) ( python … \n if %errorlevel% neq 0 pause … )`。cmd 对括号块的变量是**整块解析时一次性展开**的，`%errorlevel%` 拿到的是进块**之前**的值——就算 python 崩了，`pause` 也永远轮不到执行，闪退时连错误信息都留不下。要用延迟展开（`!errorlevel!`）或不用括号块；
3. **潜在坑：Windows 商店的假 python。** `where python` 的第一个结果可能是微软商店占位程序 `WindowsApps\python.exe`，不是真 Python，运行只会弹商店。只查"文件存在"不够，要查"真的能运行"。

### 4.4 修复（两件）

1. **重写 bat**，结构改为无括号块的顺序跳转（`if errorlevel 1` 是执行时动态求值，不受解析期展开影响）：

```bat
@echo off
chcp 65001 >nul          ← 切 UTF-8，中文提示正常显示
cd /d "%~dp0"            ← 切到 bat 所在目录
title Git 可视化工具

python --version >nul 2>nul   ← 先验证 python 真能跑，防商店假 python
if errorlevel 1 goto try_py

python git_visual_tool.py
if errorlevel 1 pause         ← 真崩了停在窗口让你看清报错
goto end
...（try_py 回退到 py 启动器；no_python 给出安装指引+下载地址）
```

并保存为 **UTF-8 无 BOM + CRLF**（本次折腾的直接教训）。

2. **Python 侧加兜底防闪退保险**：`main()` 包 try/except，启动阶段无论出什么异常，完整错误写进日志并弹出错误对话框——以后再出问题至少能"看见"。

### 4.5 验证

- 文件字节检查确认 CRLF ✅
- 实跑 bat：8 秒后 python 进程存活（界面正常开着），输出无任何报错 ✅
- 加保险后程序编译、界面冒烟测试通过 ✅

### 4.6 沉淀

> **教训：Windows 批处理是老古董，对格式斤斤计较。** 换行符必须 CRLF、变量展开时机有坑、错误处理放括号块外面。能自动化的验证就不要靠肉眼看。

（归档时这个教训被固化进 `.gitattributes`：`*.bat text eol=crlf`，git 层面锁死。）

## 5. v1.3（09-12）：第三轮折腾——全面审计

这一轮换了玩法：**不修任何东西，先通读全部代码列疑点，再逐个用实验取证，按"收益/风险"排序后只修值得修的。** 核心纪律：证据不支持的不动，不为优化而重构正常工作的代码。

### 5.1 取证方法

为每个疑点设计可复现实验（临时目录 + `GIT_CONFIG_GLOBAL` 隔离，全部离线，不碰真实配置）。11 个探针结果：

| 探针 | 实验 | 结果 |
|------|------|------|
| A | push 无远程地址 | 真实报文不在失败提示映射里 → 缺口证实 |
| B | 分支无上游 pull/push | 同上 → 缺口证实 |
| C | 远程地址写错 | 同上 → 缺口证实 |
| M | （补充验证 A/B/C 的报文形态） | 同上 |
| E | 自定义命令各种引号写法 | 常见写法正常；引号不配对抛英文 "No closing quotation" → 需修 |
| F | 5000 文件仓库的状态栏刷新 | 3 次 git 调用共 92ms → 性能没问题 |
| G | 20MB 日志整读 | 0.03 秒 → 不是问题 |
| H | 终端插入 2 万行 | 0.85 秒 → 不是问题 |
| I | 父进程退出后子进程状态 | 子进程完整跑完 15 秒 → **孤儿进程实锤** |
| J | 离线 bundle 克隆全链路 | 53 个进度事件 0→100% → 克隆/进度条健康 |
| K | 带引号路径（资源管理器"复制文件地址"） | `isdir` 返回 False → 误判证实 |
| L | 带令牌 URL 的命令显示 | 令牌明文出现在预览/终端/日志 → **泄露证实** |

### 5.2 修了什么（5 件，按收益/风险排序，每项修完立刻测试）

1. **关窗时运行中的命令变成孤儿进程**（探针 I）。修法：关窗前弹确认，确认后终止命令再退出；选"否"取消关闭。测试时**顺带抓出并修掉一个竞态**：`stop()` 读进程句柄时命令可能还没启动完成（`proc` 为 None），导致"启动瞬间点终止/关窗"杀不掉——改为停止请求标志位 `_stop_requested`，worker 启动完成后补杀。三个场景（启动瞬间关窗/运行中关窗/选取消）全部用**文件系统证据**验证（让子进程写文件，看它有没有被真的杀掉）。
2. **失败提示补齐 3 类**（探针 A/B/C/M）：push 无远程 → 引导【添加远程】+【推送并关联】；分支未关联上游 → 引导【推送并关联】；远程地址错误 → 引导【查看远程】核对。这是新手 init 完仓库后必然撞上的第二大坑。逐一用真实 git 失败场景断言中文提示出现。
3. **带引号路径误判**（探针 K）：新增 `norm_path()` 统一去引号规整，所有路径入口（输入框/浏览/配置）都过它，配置文件也存干净路径。
4. **URL 凭据明文暴露**（探针 L）：命令预览/终端/日志里 `https://user:token@...` 显示为 `https://***@...`。**只改显示层，真实执行的参数原样**（验证过写入 git 的值未打码；端口、SCP 地址、普通消息均不误伤）。
5. **自定义命令引号不配对**（探针 E）：从英文报错改为退化为按空格拆分并给中文提醒。

### 5.3 明确不修的（证据不支持，避免无谓重构）

- 状态栏刷新的三次 subprocess 调用（92ms，无感知）；
- 历史日志页整读大文件（20MB 也只要 0.03s）；
- 终端 Text 行数无上限（2 万行插入共 0.85s，且按钮集合的输出量都很小）；
- 克隆/进度条链路（本身健康）；
- 若干外观小瑕疵（失败瞬间进度条短暂显示 100%、Tooltip 的 delay 参数冗余等）。

### 5.4 审计中的插曲（两件）

1. 回归测试一度 5/11、13/14——排查后**全部是测试脚本自身的错误**（忘建仓库、用旧状态断言新命令、弹窗补丁把"确认退出"也拦成取消），不是程序问题。教训：测试脚本也是代码，也会写错，测试红了先怀疑测试本身再怀疑被测对象。
2. 某次测试忘了打弹窗补丁，真实的"配置身份"引导窗口弹了出来，被坐在电脑前的作者人工点完，配置命令成功执行——**等于用真人操作把 v1.1 的引导流程端到端验证了一遍**。"你的用户会点到你想不到的地方，哪怕这个用户就是你自己。"

### 5.5 沉淀

> 审计结束那天的感受不是"修了多少"，而是一种少有的平静：**克制也是开发的一部分。证据不支持的时候，忍住不重构，比改代码难多了。**
