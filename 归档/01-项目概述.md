# 01 · 项目概述（背景 · 意义 · 定位 · 设计理念）

## 1. 一句话与一句话展开

**一句话**：为"知道 Git 重要但不会用"的 Windows 新手打造的单文件可视化 Git 工具——把 Git 操作封装成按钮，点击时展示真实命令、执行过程与结果，让用户"边用边学"，并把所有报错"翻译成人话"。

**展开**：成品是 `git_visual_tool.py`（v1.3，1357 行，Python 标准库 tkinter，**零第三方依赖**）+ `启动Git工具.bat`（双击启动）。37 个功能按钮按七组排布，覆盖日常 Git 工作流全部环节；每次点击先亮出将要执行的真实命令，深色终端区实时回显过程，网络操作有百分比进度条，全部操作自动写日志；工具内置完整使用说明（每个按钮是干嘛的、什么时候用）；任何命令失败后自动分析 stderr，用中文提示新手最容易撞上的 9 类原因并给出下一步动作。

## 2. 项目背景（为什么做）

项目所有者在 2026 年 9 月前的真实状态：了解 Git 的重要性，但从未学会使用——打开教程就是黑色窗口里一行 `$` 冷冷地亮着，报错全英文；`git reset --hard` 听起来像"格式化硬盘"，`detached HEAD` 看不懂；一边羡慕同事优雅地 commit、push，一边把自己的项目 folder 活成"最终版""最终版2""最终版真的不改了"。

2026-09-05，所有者写下一张需求单（原文，存于 `折腾记录.md` 开头）：

> 我知道 git 是开发时经常需要的一个版本控制工具，但是我不会使用。
> 帮我开发一个 win 端的可视化工具，把 git 的各个功能封装为功能按钮，
> 但需要展示出在点击时执行了什么命令，并给出执行过程和结果。
> 保留日志。执行过程最好也加入进度条。可以在界面中使用终端这样的界面展示内容。
> 这个工具中还要附注使用说明，说明各个功能是做什么用的，应该什么时候进行使用。

需求单里藏着一个小心思：**不只是想要按钮，还想看着命令学**——按钮是拐杖，命令才是腿。这决定了"命令预览 + 终端回显"是需求本身而不是技术选型。

## 3. 开发意义（四个层面）

1. **实用层面——解决三个真实痛点**：
   - "新手第一次提交必然失败"：Git 要求提交注明作者，而身份配置装完 Git 是没有的，报错还是英文（`Author identity unknown`）。工具用【配置身份】按钮 + 启动预检 + 失败弹窗引导三层覆盖；
   - "报错全英文看不懂"：9 类失败自动诊断，把 stderr 翻译成"失败原因：…请点 XX 按钮…"；
   - "怕把仓库搞坏不敢操作"：危险操作全部二次确认且把后果写在确认框里；命令预览让用户永远知道按钮背后发生了什么。
2. **教学层面——工具即教程**："命令预览 + 过程回显"是有意的教学设计：用着用着就学会了命令。内置使用说明甚至用 ASCII 图讲清 Git 四区域模型（工作区→暂存区→本地仓库→远程仓库）。教学目标在作者身上已验证：作者正是靠这个工具完成了向日常使用 Git 的过渡。
3. **内容层面——一次完整的创作实践**：项目同时产出一篇发布于 2026-09-13 的博客文章（`博客文章.md`，含 9 张配图）和一组小红书推广文案（`文案/`）。博客记录了需求、三轮折腾与"我学到的事"，是一次"AI 结对开发"的公开复盘。
4. **方法层面——"证据先于直觉"的审计范式**：v1.3 的全面审计形成了一套可复用的工作方法（先通读列疑点→逐个实验取证→按收益/风险排序→证据不支持坚决不修），连同 11 个探针的实验设计，完整记录在 `折腾记录.md` 第三轮，对任何接手者的后续开发都有方法论参考价值。

## 4. 目标用户与使用场景

| 维度 | 说明 |
|------|------|
| 目标用户 | Windows 上装了（或准备装）Python 和 Git、但不会用 Git 命令行的新手；以及"想边用边学 Git"的学习者 |
| 核心场景 | 个人项目日常版本管理：看状态 → 看改动 → 暂存 → 提交 → 推送（每天开始先 pull 同步） |
| 次要场景 | 克隆他人仓库；分支管理（新建/切换/合并/删除）；回退与撤销（三种 reset + revert + restore）；储藏与标签 |
| 明确非目标 | ①不替代专业 GUI（SourceTree/GitHub Desktop 的可视化 diff、冲突编辑器等重交互本工具不做）②不做多人协作流支持（PR/review）③不做命令行教学替代品（是辅助不是替代）④不为 macOS/Linux 做专门启动器（代码本身可跨平台跑 `python git_visual_tool.py`，但 bat 与凭据管理器体验按 Windows 设计） |

## 5. 核心设计理念（三条，全部有踩坑史背书）

1. **给新手用的工具，不能假设任何前置知识。**
   报错必须翻译成人话，缺什么就引导补什么。——v1.1 第一轮折腾（提交必失败）的直接产物，后来具体化为：启动预检、9 类失败中文诊断、失败即弹窗引导配置身份。
2. **命令预览 + 过程回显 = 可视化学习。**
   用户永远知道按钮背后发生了什么，出了问题也看得懂日志；日志保留完整命令与输出，事后可翻旧账。——需求单第二条与第七条的落地形态。
3. **危险操作必须过确认，且把后果写清楚。**
   5 个危险按钮（reset --hard / restore / clean -fd / force-with-lease / amend）全部弹原生确认框，内容是"即将执行的命令（打码后）+ 后果说明"。——设计时就内置，博客发布时专门截图强调。

## 6. 项目性质与归属（对接手者）

- **性质**：个人学习 + 内容创作项目，不是商业产品；无用户量承诺、无 SLA、无外部依赖约束。
- **开发方式**：作者与 AI 结对——作者出需求、当第一个用户、在每轮折腾里做取舍；AI 写代码。"为什么不修"的决定、每句报错的人话翻译是作者的价值判断（博客原文原话）。
- **时间线**：2026-09-05 需求单 + v1.0/v1.1/v1.2 同日产出 → 09-12 全面审计定版 v1.3 → 09-13 发博客 → 09-21 备小红书素材 → 此后停滞 → **2026-10-08 归档封存**。
- **功能完整性**：需求单七条要求（按钮封装/命令展示/过程结果/日志/进度条/终端界面/使用说明）**全部实现**，无遗留需求；归档时点代码零改动，v1.3 即最终版。
